## Unit Tests: Professional TDD

<practice_scope>
Use tests as executable specifications for behavioral changes. Keep coverage proportional to risk and focused on observable behavior.
</practice_scope>

### Use TDD For

Apply a red-green-refactor loop for meaningful behavior changes, especially:

- backend logic, domain logic, application services, use cases, repositories, and adapters;
- parsing, validation, permissions, state machines, data transformations, and API interaction logic;
- frontend stores, reducers, selectors, data orchestration, and business behavior.

Loop:

1. Define the expected behavior as a testable case.
2. Write or identify a failing test.
3. Implement the smallest production change that passes.
4. Refactor only after green, without changing behavior.

### Do Not Force TDD For

- purely cosmetic, textual, layout-only, styling-only, animation-only, icon-only, simple markup, visual configuration, or pass-through wiring changes;
- behavior with no meaningful state, validation, transformation, rule, or public contract.

### Test Design

- Test behavior, not implementation.
- Prefer input-output assertions, observable effects, public contracts, useful errors, final state, and dependency calls that are part of the contract.
- Connect each meaningful test to a requested behavior or risk. A passing test suite is not proof of the user request unless it exercises the changed behavior.
- Avoid private-detail assertions, massive snapshots, irrelevant call ordering, over-mocking, arbitrary sleeps, and flaky execution-order dependencies.
- Use the existing framework, helpers, factories, fixtures, naming, folders, mocks, and command style.
- Do not add a new framework when one already exists.
- Mock only unstable or expensive boundaries: network, filesystem, database, clock, external services, randomness, and system processes.
- Do not chase artificial coverage. Skip trivial getters, pure types, pass-through wrappers, framework guarantees, and config without behavior.

<zombies_checklist>
Zero: empty, absent, null, undefined, no result, no config, no user data.
One: smallest valid input, item, rule, result, or call.
Many: multiple items, states, calls, ordering, aggregation, or interactions.
Boundaries: min, max, just before or after limits, dates, pagination, thresholds, near-valid invalid values.
Interface: public inputs, outputs, object shapes, errors, dependency calls, consumer-visible contracts.
Exceptions: invalid input, failed dependency, missing resource, permission, timeout, conflict, impossible state.
Simple: start with the smallest valuable test before adding matrices.
</zombies_checklist>

If tests cannot be executed, still structure the work test-first when TDD applies, state the limitation, and provide the exact command that should prove the red or green state.
