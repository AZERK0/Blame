## Architecture: Standard Professional

<practice_scope>
Design for maintainability, clear boundaries, and controlled dependencies. Apply architectural structure proportionally to the size, risk, and existing maturity of the project.
</practice_scope>

### Core Direction

- Outer layers may depend on inner layers: UI, HTTP, CLI, database, filesystem, SDKs, and external APIs.
- Application code may orchestrate domain rules and stable ports.
- Domain code must not depend on frameworks, transport objects, ORM records, SDK clients, UI objects, filesystem details, or infrastructure adapters.
- Map external shapes at boundaries instead of leaking database, API, transport, or UI objects into core logic.

### Responsibility Boundaries

- Controllers, routes, handlers, and presenters translate external input/output and call application code.
- Use cases and application services express one business intention, orchestrate dependencies, enforce application rules, and return explicit outcomes.
- Domain models hold business concepts, invariants, lifecycle transitions, and validations when real rules exist.
- Repositories and adapters isolate persistence, filesystem, network, provider, shell, container, clock, and third-party details.
- DTOs, mappers, and serializers translate between external payloads, persistence shapes, view models, and domain/application shapes.

### Structure Triggers

Add structure when it pays for itself:

- A workflow has meaningful business rules, side effects, or multiple infrastructure dependencies.
- A dependency is volatile, expensive, security-sensitive, or hard to test.
- Multiple callers need the same behavior through a stable contract.
- A known design pattern clearly reduces coupling, isolates volatility, or clarifies behavior.

Keep structure lightweight:

- Use explicit use cases for meaningful workflows.
- Use ports and adapters for volatile boundaries.
- Use entities or value objects only when identity, lifecycle, invariants, or validation matter.
- Return typed results, success/failure objects, or clear domain/application errors instead of ambiguous `null`, bare booleans, or unclassified exceptions.
- Assemble dependencies in a predictable composition root when dependencies become non-trivial.

### Frontend Architecture

- Components render state and dispatch intentions.
- Keep local UI details local.
- Put shared business state, server-backed data, workflow orchestration, and persistent app state in the project's existing store/query/service pattern.
- Do not create global stores for trivial component-local state.

<avoid>
Do not over-architect small behavior. A helper may stay a helper. A pass-through does not need six files. Do not replace a clear existing architecture wholesale when a local improvement solves the request.
</avoid>
