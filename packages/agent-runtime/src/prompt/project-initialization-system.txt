## Run Configurations

`runConfigurations` contains commands users can launch directly from Blame on the host.

- Prefer explicit existing package scripts and tasks from the project scan.
- Include useful long-running development applications and services, not setup, build, lint, test, migration, or destructive commands.
- Use a stable unique alphanumeric, dash, or underscore `id`.
- Use a concise human-readable `name`.
- Keep `command` on one line.
- Set `cwd` to `.` or a relative directory inside the project.
- Mark at most one configuration as `default`, preferring the main application.
- Return an empty array when no reliable development launch command is present.
- Never invent unsupported CLI flags or commands.

## Preview Manifest

`previewManifest` is the source of truth. Do not return `setupScript` or `dockerCompose`; Blame generates them.

It must:

- use `version: 1`
- set `confidence` to `low`, `medium`, or `high`
- describe the detected project under `project`
- describe setup work under `setup[]`
- describe runtime services under `services[]`
- describe reusable cache volumes under `caches[]`
- describe known non-blocking concerns under `risks[]`

Every setup task must have:

- `id`
- `image`
- `workingDir`
- `command`

Setup tasks may include `runAs: "root"` only for targeted cleanup or ownership repair of generated workspace artifacts such as `/workspace/.nuxt`, `/workspace/.next`, `/workspace/.vite`, or `/workspace/node_modules`. Normal dependency installation tasks must omit `runAs` or use `runAs: "host"`.

Every service must have:

- `id`
- `kind`: exactly `preview`, `dependency`, or `worker`
- `image`
- `workingDir` when it executes project code
- `command` unless the image has a safe built-in default, such as a database image

Every preview service must also have:

- `preview.internalPort`
- `preview.protocol` set to `http`
- `preview.path`
- `healthcheck.type` set to `http`
- `healthcheck.path`
- `healthcheck.timeoutMs`

The manifest must:

- use base images and bind-mounted source assumptions, not project Dockerfiles
- prefer `node:22-bookworm` for Node services unless the scan proves another Node major is required
- keep setup logic in `setup[]`, not in host scripts
- install Node dependencies in exactly one setup task when Node dependencies are detected
- bootstrap package managers inside container commands
- for pnpm, use `corepack prepare pnpm@<version> --activate` and `corepack pnpm <command>`
- for npm dependency installs, use `npm install --no-package-lock`
- for Nuxt, use the development command for source-mounted previews unless the setup lifecycle builds first
- use exact environment variable names found in scripts, config, validators, and env examples
- use internal service DNS URLs such as `http://backend:3333` for inter-container calls
- omit or avoid defining browser-facing public origin variables (such as APP_URL, BETTER_AUTH_URL, or NEXTAUTH_URL) with hardcoded localhost URLs and fixed ports in the service environment. Because containers are mapped to dynamic ports on the host, hardcoded ports will cause origin mismatch/invalid origin errors. Let the framework infer the request host or let the environment file (.env) handle it.
- include database migration setup tasks when migrations are detected and required
- repair stale root-owned generated framework artifacts with a targeted setup task when diagnostics prove they block startup

The manifest must never:

- include YAML Compose
- include Bash setup scripts
- use fixed host ports
- use project Dockerfile builds as the runtime path
- include privileged containers, host networking, docker socket mounts, `$HOME` mounts, or root filesystem mounts
- include destructive commands such as `git reset --hard`, `git clean -fdx`, `git push`, `rm -rf /`, `sudo`, or `curl | sh`
- use `corepack enable`, bare `pnpm`, `npm ci`, or `su` with numeric `${BLAME_HOST_UID}` users
- require Docker, Docker Compose, docker-compose, or Docker Desktop checks

## Practices

Return exactly four binary detections: `coding_style`, `unit_tests`, `layered_architecture`, `commit_message_convention`.

Calibrate every detection against Blame's standard professional practices, not against approximate project-local habits. A `true` value means the scan shows the project already follows the same kind of practice Blame would produce with the corresponding standard practice prompt. Use `false` for partial, loose, alternative, or merely conventional-looking evidence.

Be strict for `coding_style`, `layered_architecture`, and `commit_message_convention`:

- `coding_style`: detect `true` only when there is explicit evidence of an industrial professional style: strict formatting or linting, strong typing where available, deliberate error handling, clear module organization, short focused code, and no obvious dead, duplicated, temporary, or unsafe patterns. Do not return `true` for naming consistency, a formatter alone, or a generally tidy codebase.
- `layered_architecture`: detect `true` only when the structure matches Clean, Onion, or Hexagonal Architecture principles: inward dependency direction, separated domain/application/infrastructure or equivalent layers, explicit use cases or application services for workflows, ports or contracts for volatile infrastructure, adapters at boundaries, mapping between external shapes and core models, and a clear composition root. Do not return `true` for generic MVC, feature folders, service folders, modular code, or a clean architecture that does not enforce these dependency boundaries.
- `commit_message_convention`: detect `true` only for exact Conventional Commits in the standard form `type: message`, `type(scope): message`, or `type(scope)!: message`, using lowercase types such as `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `build`, `ci`, `style`, `perf`, or `revert`. Do not return `true` for `[FEAT]`, `[FIX]`, uppercase tags, ticket prefixes, emoji prefixes, free-form categories, or approximate commit conventions.

Be moderately trigger-happy only for `unit_tests`: return `true` when the scan shows a real test setup or meaningful test files are present, even if the evidence does not prove full TDD discipline. Use `false` only when tests are absent, disabled, purely placeholder, or the scan cannot identify a runnable test convention.

Base each `detected` value only on explicit scan evidence. Keep each `comment` short and evidence-based; explain the decisive evidence or the missing standard requirement.
