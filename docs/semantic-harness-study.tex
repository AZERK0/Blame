\begin{abstract}
Blame's current Light Semantic Harness gives a coding agent five core
primitives: search, read, edit, execute, and finish. Its distinctive contribution
is the combination of syntax-aware targeting with runtime-owned observation,
freshness checks, recoverable edits, and explicit completion decisions.
This study examines the implementation and the historical measurements,
separating executable behavior from archived proposals and proposed improvements.

The design provides useful controls over source changes. Its navigation is
primarily syntactic, reference search is lexical, and its completion policy does
not establish arbitrary acceptance criteria. Historical experiments show some
mechanical improvements, but the largest frozen comparison does not establish
general superiority over the integrated Cline SDK. The recommendation is to
retain the small tool interface, strengthen validation provenance and task
contracts, and measure quality before making efficiency claims.
\end{abstract}

\section{Scope and method}
\subsection{What is being studied}
A harness is the runtime between a model and its working environment: it exposes
actions, records observations and effects, enforces preconditions, manages
execution, and decides which completion claims it can support. The model still
chooses what to investigate and how to solve the task. A semantic harness makes
code structure usable in this loop, rather than treating every file only as
undifferentiated text.

This study covers the configured Light Semantic Harness path in
\code{packages/agent-runtime}. The five primitives are its core vocabulary,
not necessarily the entire tool list of a product session: preview, MCP,
specialist, and other configured tools may be added. Cline SDK native tools
remain a separate configurable path. UI, billing, deployment, and preview
providers are discussed only where they affect this harness's boundaries.

\subsection{Evidence and reproducibility}
The implementation was inspected in the October 7 working tree based on commit
\code{8a6ce6a5a6dc51d1b340c8360234fb8f9add0068}. That tree includes the preceding
module-extraction refactor; this study adds documentation and does not change
the harness implementation. Current behavior is traced through tool assembly,
workspace operations, aliases, edit commit/recovery, commands, the journal,
finish policy, and provider context projection. Source references appear in
Appendix~\ref{sec:sources}.

Historical evidence was recovered from the same commit's Git history, including
the former large harness study, the September 6 global measurement, and two
September 8 analysis files. Their measured bundles differ from today's working
tree. Historical results are attributed to those campaigns, not presented as
fresh measurements of the current version. This is a repository-based
engineering study, not a new systematic literature review or live-provider
benchmark.

The runtime TypeScript compiler and seven focused test files were run during
this study: 112 tests passed, with no failures or skips. The core package was
also compiled and its 13 contract tests passed. These results establish the
tested behaviors in this Linux environment, not universal correctness or
cross-platform, live-provider, or distributed-executor equivalence.

\subsection{An important historical distinction}
The former Semantic Workspace Harness and its larger protocol were
decommissioned. The historical study explicitly makes the Light design and
later corrections authoritative over its earlier proposals.

\code{packages/harness-core} still exports authorities, an evidence planner,
transaction contracts, and richer result types. In the inspected runtime,
the execution lifecycle actually imports core runtime functionality; completion
and terminal-reason contracts also appear as types. The Light tool envelope and
finish service do not invoke the core evidence planner or establish the old
four-authority architecture. Passing core tests does not prove those reference
implementations are wired into the production tool path. \src{1}, \src{8},
\src{11}, \hist{1}.

\section{Current architecture}
\subsection{A small model interface with runtime-owned mechanics}
The model selects targets, transformations, and checks. The runtime owns
canonical paths, byte offsets, content hashes, source revisions, locks, recovery,
receipts, and process observation. Keeping this bookkeeping out of model
arguments reduces opportunities to invent stale identifiers or mishandle
transaction details.

Four tools are built by \code{lightSemanticHarnessTools}; the finish tool is
assembled separately. Local calls operate through \code{LightWorkspace}.
Managed execution uses a \code{LightWorkspaceExecutor} port with the same
request/result vocabulary, backend metadata, context, and cancellation.
Briefing, journal retrieval, and attachment storage are executor operations,
not additional public coding primitives. \src{1}, \src{2}.

\subsection{Results and authority}
The current \code{LightToolResult} distinguishes \code{ok},
\code{blocked}, and \code{failed}. Successful results carry data and optionally
a receipt or image content. Blocked results identify categories such as input,
code, command, environment, or external failure, with recovery guidance where
available. Harness failures can explicitly report that an effect was already
applied and that recovery is required.

This result format is smaller than the richer core reference result contract.
A successful tool transport does not necessarily mean a successful check:
\code{run_task} can return an observed command failure in an \code{ok}
result. Consumers must inspect the operation's data, validation, and check
fields. Conversely, a post-commit journal failure must not be interpreted as
permission to replay the edit. \src{1}, \src{5}, \src{7}.

The session journal is the persisted record of requests, aliases, read coverage,
changes, validations, and terminal states. Its JSONL file is scoped by a hash
of the session identifier under \code{.blame/harness/light}. Filesystem state
is re-observed when calculating freshness and current delivery. The journal
is not a general database transaction covering every possible host effect.

\subsection{A concrete request lifecycle}
For a request to change a function's behavior, the normal loop is:

\begin{enumerate}
\item Search a relevant scope and locate the declaration.
\item Read its body and needed surrounding code. The runtime issues an alias
and records which exact bytes were exposed.
\item Submit a symbol-body replacement or a focused patch.
\item Resolve the target against current code, reject ambiguity or changed
observed content, validate the proposed content, and commit the prepared batch.
\item Request the relevant project check; inspect a running handle if needed.
\item Finish with a factual summary. The runtime evaluates current effects,
known failures, and available validation separately from SDK termination.
\end{enumerate}

If another writer changes only a neighboring declaration between steps 2 and
3, an unchanged target can be relocated. If the target body changes, the edit
requires a new observation. If source changes while a check runs, the old
check cannot establish current verification. If the task is an explanation,
the loop can end without a source mutation.

\section{How semantic the harness is}
\subsection{Syntax-level structure is useful, but bounded}
The implementation uses ast-grep/Tree-sitter parsing to extract declarations,
qualified names, signatures, and UTF-8 ranges. Capability probes cover symbol
adapters for TypeScript/TSX, JavaScript/JSX, Python, Rust, Go, Java, C\#,
C, and C++. HTML, CSS, Vue, and Svelte have structural adapters. Configuration
and unsupported formats retain raw reads, ranges, and patches.

Capabilities report whether an adapter actually loads and parses a sample;
language recognition alone is not sufficient. Navigation capability must also
be distinguished from syntax-validation authority, particularly for C/C++
and their build-dependent language features. \src{3}.

These mechanisms help select declaration boundaries and preserve wrappers
such as exports, decorators, and templates. They do not establish type
correctness, resolve overloads throughout a project, prove rename safety,
or reconstruct every dependency. The current references mode explicitly
returns lexical fallback. It can find useful candidates, but identical names
may refer to different entities, and computed or generated references may
remain invisible.

\subsection{Aliases encode observation, not permanent identity}
Aliases such as \code{s1} carry a path, qualified name, kind, byte range,
file hash, target-content hash, and observed intervals. If the file is
unchanged, the byte target remains directly usable. If the file changed, the
runtime attempts to resolve the declaration again by identity.

A unique relocated declaration with unchanged observed content can still be
edited. Changed content requires a fresh read; multiple candidates produce
an explicit resolution problem instead of a guess. This is a practical local
rebase mechanism, not a stable compiler symbol ID across arbitrary renames,
duplicate declarations, macro expansion, or generated code. \src{4}.

The coverage check matters as much as the name: seeing a declaration signature
does not establish observation of the whole body. The runtime tracks observed
byte intervals and requires the affected span to be covered for the relevant
symbol operation. This prevents a compact outline from becoming implicit
authorization to discard code the agent has never seen.

\subsection{Observation and context freshness}
Read coverage is keyed by consumer, context generation, path, and content
hash. Intervals can merge and repeated reads can return uncovered portions
or a covered receipt. Context generation is obtained from explicit metadata
or a compaction-summary identity. File mutations invalidate relevant coverage.

This separates exposure of exact bytes from permission to omit them in a
particular context. Neither claim proves the model understood or retained
the code. A compaction summary must not create source knowledge merely by
mentioning a symbol. Coverage and alias restoration are bounded, which limits
memory growth but also means the harness is not an unbounded persistent
knowledge graph. \src{4}, \src{9}.

\subsection{When symbols help, and when patches are appropriate}
Symbol edits are most useful for an already observed, clearly bounded
declaration: replacing a body, inserting around a declaration, or deleting
one unambiguously resolved entity. Focused patches remain appropriate for
small changes within a declaration, mixed markup, imports, configuration,
or edits that do not map cleanly to one supported symbol.

Forcing every edit through a symbol API would add friction without establishing
more correctness. The frozen global campaign recorded only six requested
symbol operations against 101 patches. That campaign therefore tests the
overall harness loop more than it isolates the value of semantic editing.
Keep both routes, expose which engine produced a target, and measure their
use and rejection reasons separately. \hist{2}.

\section{Edit correctness, concurrency, and recovery}
\subsection{Preparation and commit}
An edit batch is planned against one source snapshot. Target resolution,
overlap checks, observed-content preconditions, and applicable content
validation happen before committing the changes. Scoped patches must agree
with the target path and stay within the allowed declaration boundary.

The commit service takes an exclusive cooperating lock under
\code{.blame/harness/light-write}, recovers a pending interrupted write,
checks the expected source revision, and checks each file's preimage.
It writes a durable pending record, applies individual file updates
atomically, and removes the pending record on completion. Controlled
failures trigger rollback. No-op content changes are filtered. \src{5}.

The important invariant is that a prepared edit may not silently replace
different current source. The implementation checks both a workspace revision
and per-file content. The global revision is conservative: unrelated source
changes can invalidate a preparation even when the target itself is unchanged.

\subsection{Recovery preserves ownership}
Recovery accepts a path only when its current content matches the recorded
before or after image. A newer third state is a conflict; the runtime preserves
it rather than overwriting it with a rollback. Harness readers acquire the
same lock and wait until the controlled batch or recovery completes.

A receipt-persistence failure after the write is materially different from
a preparation failure. The former can leave the requested source effect in
place. The result must expose that fact and a recovery requirement so the
agent does not retry a mutation that already happened. Targeted tests exercise
this distinction as well as interrupted multi-file recovery and concurrent
user edits.

\subsection{The atomicity claim has limits}
This is recoverable batch behavior for cooperating harness operations,
not a filesystem-wide transaction respected by every program. Individual file
updates are atomic, but an editor, build process, or shell command that ignores
the lock can observe intermediate files or race a check and write. Recovery
checks also cannot make a noncooperating writer participate retroactively.

Commands run against the actual worktree and may create effects outside the
source snapshot, including external services. They are not universally executed
inside the old proposal's ephemeral overlay. Source rollback must not be
described as rollback of all command effects.

The right guarantee to publish is precise: revision and preimage checks,
serialized cooperating access, crash recovery, and preservation of detected
concurrent changes. Stronger isolation requires a separate execution boundary
and dedicated adversarial testing.

\section{Execution and validation evidence}
\subsection{Command execution is an observed operation}
\code{run_task} supports ordinary commands, recognized project tasks,
Node dependency changes, and inspection of a running command. Source snapshots
before and after execution detect mutations even when a command fails.
Known project checks have task IDs and package scopes; a generic successful
inspection command is not automatically a validation.

A longer command can return a running handle and output cursor. Inspection
continues that command rather than launching it again. The active process map
is in memory: journal durability does not imply a process handle survives
replacement of its runner. The executor protocol carries cancellation,
but cancellation must also work at the operating-system process and output
capture levels. \src{2}, \src{6}.

Command policy accounts for managed preview ownership and some side-effect
restrictions. This does not establish a universal shell sandbox. Deterministic
formatter effects and supported dependency operations are tracked through
the relevant services; other ecosystem operations remain commands.

\subsection{Exit, execution, outcome, and proof are different}
The check observation deliberately separates:

\begin{itemize}
\item process state: exited, timed out, cancelled, or running;
\item execution: tests observed, zero tests, or no execution observed;
\item outcome: passed, failed, or unknown;
\item selected scope and whether selection is confirmed;
\item freshness and evidence origin, including invocation-attributed reports.
\end{itemize}

An exit-zero command with no observed tests stays unknown. A green fragment
before interruption does not establish a passing run. Old report files cannot
validate a silent new invocation. Counts and diagnostics are taken from bounded
final summaries or invocation-attributed reports. \src{7}.

There is a particularly important current limitation: \code{observeCheck}
leaves selection unknown and, absent detected changes, freshness unknown.
Pre/post source equality alone cannot exclude external writers. Even a
successfully observed test run is recorded by the task runner as validation
status unknown; failed tests are recorded as failed. Such test observations
therefore do not currently promote delivery to verified through the generic
passing-validation path.

This is conservative and prevents unsupported claims. It also means a useful
test execution and a formally admitted validation are visibly different.
Users and downstream UI must not turn \code{outcome: passed} into a blanket
verified badge. Conversely, verified delivery obtained from a build or
typecheck does not imply behavioral tests or acceptance criteria passed.

\subsection{Freshness is mostly source-based}
The journal admits current validation only when its source revision and
covered file hashes match current source. Package scope prevents a check in
one package from automatically covering another. The global revision can
invalidate evidence after an unrelated change, trading precision for simpler
conservative behavior.

The separate workspace environment revision hashes Node manifests and
lockfiles; dependency readiness largely checks for the root
\code{node_modules} directory when dependencies are declared. This is not
a fingerprint of the installed dependency graph, runtime version, operating
system, environment variables, database state, or remote services.
The Light journal's validation record does not bind a complete environment
revision. \src{6}, \src{7}.

Consequently, unchanged source is not sufficient to prove that a later
environment is equivalent. A future validation receipt should distinguish
source identity, command/task identity, selected scope, invocation identity,
and the relevant environment identity without exposing secret values.

\section{Completion: what finish actually means}
\subsection{Current policy}
The finish service obtains current source effects and fresh journal
validations. Known fresh code-validation failures block completion.
It considers relevant tasks that were already requested in the session,
reuses available current passing validation, and can refresh selected stale
checks. It does not introduce a new unrelated build merely because one
exists in the task catalog. \src{8}.

This policy addresses a measured failure mode: in two historical Material UI
runs, an additional build imposed at finish failed even on the intact
repository, although the first submitted patch already passed the required
external tests. The resulting loop added 34 and 32 model requests and 11 and
10 refusals. Limiting finish to previously requested checks fixed that
mechanical cause without adding a repository-specific exception.
\hist{1}, section 21.62.

\subsection{Delivery, verification, and acceptance}
Accepted completion has separate fields for delivery and verification.
Changed source with admitted passing validation covering the changed paths
can be verified. Changed source without such validation is unverified with
a reservation. No current mutation can yield verification not applicable.
Task termination in the SDK is not by itself this domain decision.

However, the inspected session setup puts the objective into a free-text
acceptance-criteria array and sets \code{effect_requirement: none}.
The finish service does not interpret those arbitrary criteria into
independently demonstrated obligations. Its decision marks delivery satisfied
without solving functional acceptance. An explicit
\code{source_change} contract would require an effect, but the inspected
default does not supply one. \src{1}, \src{8}.

Two consequences follow. First, the harness can correctly accept explanations
without manufacturing edits. Second, an empty effect is not a mechanical proof
that an implementation request was fulfilled. Verified means coverage under
the admitted validation policy, not correctness under every user requirement.
The core reference evidence planner must not be cited as filling this gap:
it is not called by this finish path.

\subsection{Where the policy should evolve}
Keep finish small and deterministic. Improve explicit task intent and proof
admission before introducing a general obligation solver. A task can specify
whether a source effect is required and which externally checkable obligations
matter. Checks that are unavailable should remain unavailable; the runtime
must not invent success, silently erase a failure, or repeatedly select new
checks while trying to make a terminal decision.

The useful target is a truthful completion statement: what changed, what
actually executed, which source/environment it observed, which scope it
covered, and what remains unverified.

\section{Context, cache behavior, and memory}
\subsection{Stable projection instead of rewriting every old message}
The canonical transcript and provider projection serve different purposes.
The current stable message builder retains projected blocks already sent
while the canonical prefix remains unchanged and appends new projected
content. A real canonical reset or compaction creates a new projection basis.
Fresh observations are still exposed. \src{9}.

This avoids rewriting historical tool results on every later read or
validation, which can disrupt provider prefix caching. It does not minimize
all context bytes: retaining a useful earlier observation can be preferable
to repeatedly rebuilding a shorter prefix. Overlapping reads can project
novel content while preserving necessary exact source and metadata.
Multimedia and compaction tests exercise preservation across these paths.

Reported context byte counts measure the projection, not billed tokens.
Tokenization, cached-input accounting, transport behavior, and prices belong
to provider observations. A smaller transcript is not automatically a cheaper
or more successful run.

\subsection{Optional tool arguments are part of the effective interface}
Provider schema handling affects whether an agent can actually omit optional
arguments. The Responses compatibility layer supplies \code{strict: false}
when a function tool has no explicit strict setting; local schema validation
still controls the harness input.

In a historical diagnostic campaign, candidate reads omitted optional ranges
45 times out of 64, compared with zero out of 90 before the correction.
The same campaign associated stable prefixes with higher reported cache use.
Several changes were bundled together, and complete historical HTTP bodies
were not reconstructed; these are not isolated causal estimates. \src{9},
\hist{1}, section 21.56.

\subsection{Project memory is bounded retrieval}
Verified completion can generate a memory candidate containing the objective,
summary, changed-file hashes, symbols, and a validation identifier. Retrieval
scores relevance and checks current file hashes before constructing a small
briefing; the implementation bounds the number and size of selected memories.
This is useful reuse of previous engineering facts, not a learned global
semantic model. \src{10}.

The inspected archives do not establish a longitudinal performance gain from
memory. Hash freshness also does not prove that a remembered summary is
complete or still relevant under every unchanged-file dependency. Memory
benefits require a separate repeated-task experiment with leakage controls.

\subsection{Why campaigns must remain separate}
The archive contains successive diagnostic campaigns and frozen comparisons.
They use different versions, tasks, and policies. Summing them into one
success rate would mix version selection with confirmation and would double
count familiar tasks. Provider cost is reported or SDK-estimated cost, not
an independently verified invoice. Failed and interrupted trials remain part
of quality measurement.

\subsection{External application tasks and the corrected finish policy}
The September 8 external-application comparison had six tasks with two
repetitions per arm. Audit reduced Cline from 11/12 nominal successes to
8/12 and Light from 12/12 to 7/12. Some trajectories accessed subsequent
public solution material. The distinction between official test success and
independently solved success materially changes the conclusion.

Cline's total token and cost usage was incomplete in one trial; the complete
Light totals cannot be turned into a precise global savings claim against
that incomplete control. Agent times were 3,145.36 seconds for Cline and
3,074.92 for Light. These small differences on six known tasks are not a
confirmation of general performance. \hist{3}.

A separate frozen comparison of the corrected finish policy used three known
tasks, three arms, and two repetitions. The corrected version passed 5/6,
while both the preceding Blame and Cline passed 6/6. It reduced requests from
138 to 75 and time by 32.5\% against preceding Blame, addressing the measured
finish loop. Against Cline, it used 37.1\% fewer tokens and 32.3\% less reported
cost, but took 40.7\% more agent time and had lower observed quality.
Efficiency at unequal quality is not a dominance result. \hist{4}.

\subsection{Rejected changes and verifier instability are evidence too}
The latest archived prompt experiment increased time, requests, tokens, and
cost against its control and was reverted. It improved some observed test
execution without improving the overall diagnostic trajectory.

The archive also records a benchmark-title issue identifier leading through
a web redirect to a later merged solution. Neutral benchmark titles and
accurate final-response URLs were then corrected. These corrections followed
the frozen campaign and must not be retroactively credited to its scores.
An asynchronous Vue verifier also failed different checks on replay before
passing the same captured patch; original scores were retained.

These findings favor transparent provenance audits and fixed versions over
selecting only favorable reruns. The four later campaigns' 96 trials across
12 distinct tasks must remain separate. General stable superiority over Cline
remained unproven in the latest historical conclusion. \hist{1}, section 21.64.

\section{Recommendations}
\subsection{Priority 0: truthful validation and completion}
First, document and expose the existing proof distinctions consistently:
process exit, observed assertions, selected scope, freshness, admitted
validation, and functional acceptance. Unknown evidence must remain unknown
through the journal, notifications, UI, and final summaries.

Next, make task effect intent explicit at the application boundary. Use
\code{source_change} where an implementation task actually requires an effect,
while preserving no-effect explanations and justified already-satisfied tasks.
Do not infer a complicated acceptance contract from arbitrary text at finish.
Any already-satisfied path needs an explicit explanation and relevant evidence.

Finally, design proof admission for real test invocations. A proposed receipt
should bind the selected task, invocation ID, source snapshot, relevant
environment, executed counts, final process state, and scope. Prefer an
isolated immutable source snapshot when claiming current freshness.
Do not promote today's unknown observations merely by changing a label.

Success criteria: silent exit-zero tests stay unverified; interrupted green
output stays unverified; stale or wrong-package checks cannot verify changed
code; known relevant code failures remain blocking; no unrelated check is
invented during finish.

\subsection{Priority 1: execution and recovery contracts}
Retain the existing preimage and pending-journal protections. Clarify which
callers participate in the lock, which effects are outside source tracking,
and how callers respond to committed-but-unrecorded results.

Prioritize process supervision and cancellation across inherited output
descriptors, child processes, and managed executor replacement. Historical
timeouts and orphan workers affected measured outcomes more directly than
adding another semantic abstraction. Extend durable execution identity only
if continuation across runner replacement is a supported product requirement;
do not imply that in-memory handles already provide it.

Success criteria: cancellation returns within a specified bound, child processes
are handled under a declared policy, missing handles produce factual recovery
guidance, and rollback never knowingly overwrites a newer user edit.

\subsection{Priority 1: reproducible evidence for an open repository}
Keep a small English documentation set, but make experimental conclusions
reproducible. Preserve campaign IDs, frozen commit/bundle hashes, task lists,
verifier identities, usage completeness, and analysis commands in a compact
manifest. Large traces can live in a versioned artifact release or retained
Git history; a summary should point to them and retain negative results.

Before claiming a portable open-source harness, document its real local
execution contract and optional managed-executor requirements. A local core
path exists, but this study does not validate a clean end-to-end self-hosted
product install. License and paid-service decisions are separate from these
architectural guarantees.

\subsection{Priority 2: deeper semantics where demand justifies it}
Add compiler/LSP reference resolution through an optional capability port
only for measured high-value cases, such as ambiguous cross-file references
or safe renames. Preserve lexical and raw fallbacks with declared engine
identity. A language server introduces lifecycle, configuration, environment,
and stale-index problems of its own.

Measure target ambiguity, wrong-scope candidates, patch rejection causes,
and reread cost before investing in a project-wide graph. Keep the five
core primitives unless a demonstrated workflow cannot be expressed clearly
through them.

\subsection{Refactoring boundaries worth preserving}
The previous SDK module extraction helps navigation through the coordinator,
but file-size reduction is not the harness study's main conclusion.
The remaining useful boundaries are:

\begin{itemize}
\item model/SDK adaptation versus the Light operation port;
\item workspace observation and target resolution versus edit preparation;
\item recoverable source commit versus command/process supervision;
\item raw check observation versus proof admission;
\item proof admission versus completion policy;
\item canonical transcript versus provider context projection.
\end{itemize}

Keep application services dependent on explicit ports and DTOs, with provider,
filesystem, parser, and process details in adapters. Avoid a new monolithic
semantic manager or a second competing evidence authority. A future
promotion of core reference contracts into production requires explicit
adapter wiring and migration tests, not just shared type names.

\section{A proposed confirmation protocol}
No new paid-model campaign was run for this study. The next comparison should
be specified before results and should evaluate one frozen implementation.

\begin{enumerate}
\item Freeze runtime, prompt, schemas, model, effort, task set, dependency
images, verifier, budgets, and both arms' versions. Declare per-tool timing
policies and shared lifecycle components.
\item Select tasks before execution across language, repository size,
multi-file scope, environment dependency, and context length. Keep a genuine
holdout separate from diagnostic tasks used to choose the version.
\item Pair arms close in time, balance their order, and repeat by task.
Treat each task and its repeated arms as one inference block.
\item Retain failures, timeouts, missing usage, and original verifier scores.
Predeclare replay rules for infrastructure and flaky-verifier investigation.
\item Audit for solution leakage, including titles, issue identifiers,
redirected pages, and retrieved reference patches. Separate nominal test
success from audited independent success.
\item Measure audited success first; then compare cost and time under a
predeclared quality requirement. Record actual provider input/output/cache
usage without counting cached or reasoning tokens twice.
\item Report agent time, environment preparation, verification time, command
waits, finish requests, mutation types, rejection reasons, and compaction.
Do not add parallel tool durations as though they were elapsed time.
\item Use paired intervals, state missingness, and keep complete-case resource
analyses secondary. Do not pool versions or convert incomplete totals into
exact savings.
\end{enumerate}

For a semantic claim, include tasks requiring cross-file resolution and
measure whether structural operations actually occur. For a compaction claim,
include tasks that actually compact. For memory, compare repeated task
sequences with memory on and off under leakage controls. These are distinct
experiments, not properties demonstrated by one overall benchmark score.

\section{Engineering judgment}
Retain the Light Semantic Harness as a small, inspectable control layer.
Its strongest supported value is safer interaction with a changing worktree:
observed targets, guarded effects, recoverable writes, and honest separation
of execution from verification.

Prioritize validation provenance, explicit task intent, and process supervision
before adding a broad semantic graph or restoring the archived protocol.
Publish performance claims only when a frozen comparison preserves audited
quality and has complete resource accounting. The existing evidence supports
specific mechanical improvements; it does not support a general claim that
this harness is faster, cheaper, or more capable than Cline.

tests, old reports, finish without an invented build, executor transport,

These focused checks do not rerun the whole application, resolve previously
reported repository-wide baseline failures, or constitute fresh model
benchmarking. They do not establish complete test-proof admission, arbitrary
acceptance validation, or noncooperating filesystem isolation.
