# Validation de fin de tâche — comparaison diagnostique figée

Cette campagne mesure une seule modification fonctionnelle : `finish_task` sélectionne ses validations parmi les tâches déjà demandées dans la session. Il réutilise les réussites fraîches, rafraîchit les vérifications devenues périmées et conserve le blocage des échecs connus. Sans vérification reconnue, il rapporte une livraison non vérifiée. Il ne choisit plus un nouveau build simplement parce que le catalogue le contient. La description de l’outil et le prompt sont alignés sur ce comportement. Aucun nouvel outil, état, dépendance ou appel modèle n’est ajouté.

La version antérieure est le bundle `189d22d92b0752aa92f9540ee8f966a8c08621147ddd9c65ec1556f2f0b2f75f`, source `e723fd40`. La nouvelle version est construite au commit `7c50d3ee` après build, lint et suite complète réussis ; son empreinte figure au manifeste avant les appels modèle. Cline utilise les outils et le prompt natifs du SDK 0.0.81 dans le runner de la nouvelle version. Les trois bras conservent Luna high, sans Sol, identifiant projet ni mémoire projet.

Dix-huit essais : Material UI, Jackson et Serilog, trois bras, deux répétitions. Deux lots de neuf essais, deux conteneurs simultanés, ordre des tâches et bras inversé à la seconde répétition. Aucun retry, choix du meilleur essai ou arrêt sur résultat favorable. Les trois tâches sont connues et diagnostiques : Material UI expose le défaut ; Jackson et Serilog sont les premières réservations Java et C# dans l’ordre initial de préparation. La sélection est enregistrée avant le correctif. Elle ne constitue pas un holdout ni une estimation de supériorité globale.

Les images et vérificateurs sont ceux de la campagne applicative précédente. Leurs contrôles base 0 / référence 1, empreintes et révisions sont conservés et réutilisés, sans prétendre les avoir réexécutés. Les replays séparés du build de base et du patch Material UI capturé au premier `finish_task` doivent être terminés avant cette campagne. Aucun conteneur de contrôle ou autre benchmark ne s’exécute simultanément aux agents. Les changements de source évalués restent figés jusqu’à la fin des deux lots.

Chaque bras reçoit l’issue originale et la même consigne additionnelle : travailler depuis le checkout fourni ; documentation générale, dépendances et références historiques explicitement liées dans l’issue autorisées ; récupération de révisions ultérieures, de correctifs de pull requests et de solutions publiées à cette issue interdite. Cette consigne amont répond aux récupérations de solutions constatées dans la campagne précédente. Elle préserve notamment le commit de régression historique cité par Serilog. Aucun blocage web runtime ni indice de réponse n’est introduit. Les deux campagnes ne sont pas fusionnées.

Budgets : 4 CPU, 8 Gio, 64 itérations, 900 secondes agent comprenant la création du SDK et 1800 secondes vérificateur. Les délais de commandes restent ceux des configurations livrées : 120 secondes Blame et délai natif Cline configurable. Le Node du projet est préservé ; le lanceur possède son propre Node compatible. Les tests officiels sont injectés après arrêt de l’agent. Les solutions de référence et les diagnostics de l’analyste ne lui sont jamais fournis.

Le bilan inclut tous les essais, les échecs et leurs ressources. Il distingue score officiel, résolution indépendante auditée, suite complète, complétion du harness, requêtes, temps, tokens et coût estimé du SDK. Un usage incomplet reste inconnu et exclut tout total exact pour le bras ; les comparaisons de consommation sont limitées aux tâches entièrement réconciliées dans les deux répétitions et les deux bras comparés. Les comparaisons prévues sont nouvelle version / antérieure et nouvelle version / Cline. Bootstrap descriptif de tâches entières, 20 000 tirages, graine 20260908 ; répétitions séparées, ratios médians et retrait d’une tâche. Trois tâches ne suffisent pas à établir un gain global stable.

Les métriques de diagnostic comprennent les refus de `finish_task`, les validations déclenchées automatiquement, les requêtes après la première tentative de fin et les rejets d’édition. Aucun résultat final favorable ne suffit à prouver qu’une validation interne était correcte. Le rapport conserve explicitement les livraisons non vérifiées et les essais qui ont utilisé un correctif public malgré la consigne.
