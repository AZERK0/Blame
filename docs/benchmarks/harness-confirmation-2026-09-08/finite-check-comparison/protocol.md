# Invocations de validation — comparaison diagnostique figée

La seule modification évaluée est une clarification du prompt : inspecter les commandes de test du projet, choisir une vérification ciblée qui se termine, corriger l’invocation si les résultats sont déjà affichés mais que le processus reste ouvert, et confirmer que les tests prévus ont effectivement été exécutés. Un code de sortie nul seul ne suffit pas. Aucun flag automatique, variable d’environnement, parseur de résultats supplémentaire, timeout modifié, nouvelle dépendance ou restriction aval n’est introduit.

Le témoin Blame est le bundle `148bca6eb119fead680e4cbd3205ee45efdf176c7c58f9ef182b27e9c08c8069`, source `7c50d3ee`. Il contient déjà le correctif de fin de tâche. Le commit et l’empreinte du nouveau bundle sont enregistrés au manifeste avant les appels modèle. Cline conserve le prompt et les outils natifs du SDK 0.0.81 dans le même runner. Luna high reste le seul modèle ; pas d’identifiant projet, de mémoire projet ni d’essai Sol.

Dix-huit essais : Material UI, Vue et Serilog, trois bras, deux répétitions, deux lots de neuf et deux conteneurs simultanés. La seconde répétition inverse l’ordre des tâches et des bras. Aucun retry ni remplacement après observation du résultat d’un agent de cette campagne. Tous les cas sont connus et diagnostiques. Material UI et Vue ont présenté des commandes restant ouvertes après les assertions. Serilog a présenté une commande `dotnet test --no-restore` silencieuse, terminée à zéro, suivie d’une affirmation erronée de vérification.

La sélection initiale prévoyait Jackson comme contrôle Java. Avant tout gel ou essai de cette campagne, l’échec Serilog observé dans la campagne précédente motive son remplacement par ce diagnostic C#. La sélection initiale et l’amendement sont conservés. Il s’agit d’une sélection de cas défavorables pour comprendre un mécanisme général, pas d’un holdout ni d’une estimation de supériorité globale.

La campagne précédente et le replay isolé Serilog doivent être terminés avant ce gel. Le replay conserve le patch et le test écrits par l’agent, compare l’invocation sans restauration à celle avec restauration, et n’utilise aucun patch de référence ni test caché. Les diagnostics de l’analyste et réponses propres aux tâches ne sont jamais fournis aux modèles évalués.

Les trois bras reçoivent l’issue originale et la même consigne d’indépendance déjà employée dans la comparaison de fin : checkout fourni, documentation générale, dépendances et références historiques explicitement liées autorisés ; révisions ultérieures, correctifs de pull requests et solutions publiées à l’issue interdits. Cette consigne commune est distincte de la modification du prompt Blame. Aucun blocage web runtime n’est ajouté.

Images, matériel de test et contrôles base 0 / référence 1 proviennent de la campagne applicative initiale ; ils sont réutilisés, pas présentés comme de nouveaux contrôles. Le vérificateur restaure les tests officiels après arrêt de l’agent et distingue FAIL_TO_PASS/PASS_TO_PASS, suite complète et absence de tests requis. Material UI conserve ses échecs annexes préexistants. Les images et entrées évaluées restent figées jusqu’à la clôture des deux lots. Aucun autre conteneur de contrôle ou benchmark ne s’exécute simultanément.

Budgets communs : 4 CPU, 8 Gio, 64 itérations, 900 secondes agent comprenant la création du SDK, 1800 secondes vérificateur. Les délais de commandes restent ceux des configurations livrées : 120 secondes Blame et délai natif configurable Cline. Le Node du projet reste intact, le runner utilise son Node compatible privé.

Le bilan conserve tous les essais, y compris échecs, expirations et récupérations d’oracles confirmées. Scores officiels et audités, validation interne, requêtes, temps, tokens et coût estimé SDK sont distincts. Toute consommation incomplète rend le total exact de son bras inconnu ; les comparaisons de consommation utilisent seulement les tâches réconciliées dans les deux répétitions et les deux bras comparés. Comparaisons prévues : nouvelle version / précédente et nouvelle version / Cline. Bootstrap descriptif de tâches entières, 20 000 tirages, graine 20260908, répétitions séparées et retrait d’une tâche. Aucun mélange avec les campagnes précédentes.

Le diagnostic compte aussi les commandes expirées, les résultats de tests réellement visibles, les refus de patch et de fin, ainsi que les requêtes après la première tentative de fin. La réussite d’un processus ne devient jamais, par convention d’analyse, la preuve que les assertions ont été exécutées. Un résultat favorable sur ces trois cas ne constitue pas un gain global stable.
